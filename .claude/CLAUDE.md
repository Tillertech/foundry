# Foundry

Nx 23 npm monorepo. `npm install` resolves cleanly - never add `--legacy-peer-deps`; fix the peer conflict instead. Apps: `apps/api` NestJS 11 (webpack build → dist/apps/api/main.js), `apps/client` Angular 22 CSR SPA standalone+signals (spartan-ng, tailwind4, ng-icons/lucide, ngx-echarts) for workspace owners, `apps/client-portal` Angular 22 CSR SPA (same stack) for their clients, plus api-e2e/client-e2e/client-portal-e2e. No SSR — both apps are fully auth-gated with no public/SEO surface, so they ship as client-rendered SPAs. `libs/ui/*` are spartan-ng's own per-component CLI-generated libs (`@spartan-ng/helm/<name>`, ng-packagr); `libs/shared/util` and `libs/shared/ui` (`@foundry/shared-util`, `@foundry/shared-ui`) are hand-authored source libs holding code duplicated between `client` and `client-portal` — both path-mapped in tsconfig.base.json, both consumed straight from source (no separate build step needed by the apps).

## Nx

Run tasks through nx (`npx nx build|serve|test|lint <project>`, run-many, affected); never the underlying tool directly. Never guess CLI flags — check `--help` or nx_docs (nx_docs only for advanced/unfamiliar options, not basics). Use nx-workspace skill for workspace exploration; nx-generate skill FIRST for any scaffolding. Plugin best practices: node_modules/@nx/<plugin>/PLUGIN.md when present. Nx MCP server available.

## Prisma

Schema `apps/api/prisma/schema.prisma`; all prisma CLI calls need `--config=apps/api/prisma.config.ts` (or cwd apps/api). Client generated to `apps/api/src/generated/prisma`: model types export as `<Name>Model` (e.g. `ClientModel`), enums in `generated/prisma/enums` are const objects. Decimal columns serialize to string in JSON. Runtime connects via @prisma/adapter-pg in src/prisma/prisma.service.ts (DATABASE_URL, default localhost:5433/foundry). Regenerate after schema edits (`just generate`, runs inside the api container — host-side `npx prisma generate` often EACCESs on the generated dir since docker last wrote it as root).

## Docker / just

Dev: `just develop` → docker-compose.local.yml: db 5433, redis 6379 (container foundrycache), mailpit 1025/8025 (UI), api 3000, client 4200, clientportal 4201; `just studio` (profile tools, 5555); `just migrate "name"`, `just generate`, `just status`, `just reset`; env .env.docker. Prod: `just prod-build|prod-up|prod-down|prod-logs|prod-migrate` → docker-compose.production.yml + .env.production (template .env.production.example). Dockerfile.api.{local,production} and Dockerfile.client.{local,production} at repo root; the client Dockerfiles take a `PROJECT` build arg (`client` default, or `client-portal`) selecting which Angular app to serve/build. Api prod image runs prisma migrate deploy then node main.js, hbs templates copied to /app/mail/templates. Client prod is a static SPA served by nginx:alpine on port 80: for `PROJECT=client`, nginx.conf (repo root) is baked in at build time and reverse-proxies /api + /uploads → foundryapi:3000 (runtime DNS via docker resolver 127.0.0.11); for `PROJECT=client-portal`, apps/client-portal/nginx.conf.template is installed instead and its `${API_URL}` is substituted by the nginx image's own entrypoint at container start, so the same image can point at any API host. Both SPA-fall-back to index.html. client:serve dependsOn api:serve — use `--excludeTaskDependencies` to serve alone (client-portal:serve has no such dependency). Containers mount the repo but keep their own `/foundry/node_modules` (anonymous volume) - after adding a dependency on the host, run `npm install` inside each container that needs it. They also tmpfs `/foundry/.nx` — nx's PID-keyed running-task DB must not be shared across host/containers or serve waits on phantom processes. client:serve sets allowedHosts localhost+127.0.0.1 (dev-server hard-400s other Host headers) and proxies /api via proxy.conf(.docker).json — client-portal has its own copies of the same two files.

## API (apps/api/src)

- Global prefix api/v1; Swagger /api/docs (dev only, bearer auth); ValidationPipe whitelist+forbidNonWhitelisted+transform+implicitConversion. Relative imports only (no src/ alias). tsconfig types: node,multer.
- One module per aggregate (module/controller/service + dto/ + entities/): identity/auth, workspaces, clients, projects, invoices, quotes, payments, expenses, documents, notification, events, storage, prisma, common/pagination, client-portal, portal-users, portal-auth, portal-api, portal-public.
- Auth: @nestjs/jwt global via AuthModule (JWT_SECRET, JWT_EXPIRES_IN 7d); payload {sub,email,name}; JwtAuthGuard + @CurrentUser(). Signup creates user + default workspace atomically (default workspace = oldest, GET /workspaces/default) but issues NO token — it emails a 6-digit code and the user confirms via POST /auth/verify-email (sets user.emailVerifiedAt) which returns the JWT. Login is two-step OTP too: POST /auth/login checks the password then emails a sign-in code (returns a challenge, no token; 403 if email unverified → re-sends verification), POST /auth/verify-login exchanges the code for the JWT. All OTPs: 6-digit, bcrypt-hashed in user.otpSecret as `hash:expiresMs` (15min TTL), single-use. Event payload interfaces + names live in common/events (AuthEvents/InvoiceEvents/PaymentEvents/FileEvents/PortalEvents); auth mails go via issueOtp(user, event) → AuthEvents.{PASSWORD_RESET,EMAIL_VERIFICATION,LOGIN_OTP}_REQUESTED.
- Ownership: queries scoped through workspace.ownerId chain (project→client→workspace etc). Expenses carry their own workspaceId (scope `workspace: { ownerId }`, derived from the project on create/move, else the requested/default workspace; legacy unattributable rows are NULL and visible to nobody). Moving a project to another client (ProjectsService.reassignClient) unshares it from the old client's portal, shares it into the new one's and moves its expenses' workspace, in one transaction. Documents likewise carry their own workspaceId (from the client, else the project's client, else requested/default workspace; a client+project pair must agree, since the portal lists documents by client OR shared project); reassignClient also refiles a project's documents. Payments must reference an invoice of their own client. The default-namespace EventsGateway is unauthenticated and must never broadcast domain events (it used to leak every upload's storage URL); there is deliberately no public /uploads static route - files are only served via owner/portal-scoped download endpoints.
- Lists: cursor pagination — PaginationService.paginate(delegate, baseArgs, {cursor,take,orderBy,baseUrl,includeCount}) → {count,next,previous,results}; swagger via ApiPaginatedResponse(Entity); orderBy field must exist on model (projects startDate, payments/expenses date, documents uploadedAt, else createdAt).
- Currencies: stored as plain 3-letter ISO 4217 codes (`VarChar(3)` + a `^[A-Z]{3}$` CHECK), no Prisma enum - common/currency.ts has DEFAULT_CURRENCY, CURRENCY_SCHEMA (swagger) and @IsCurrencyCode(); the pickable catalogue is CURRENCIES in libs/shared/util. Records keep the currency they were written in; projects have no currency of their own - a project's budget/hourlyRate are in its client's currency. GET /invoices/exchange-rates returns rates into the default workspace currency only for currencies the owner's records use, omitting any whose rate can't be fetched; reports are cached per workspace currency.
- Project.notes is internal: the portal-api project queries `omit` it (they `include`, so every other Project column is serialized) - keep it omitted if those queries change.
- Invoices/quotes: nested items create; update with items replaces all (deleteMany+create); numbers auto-generated INV-/Q-. POST /invoices/:id/send → status sent + event invoice.sent → NotificationService (pdf attachment + hbs mail + ws emit to owner room). PdfGeneratorService lives in invoices/ (no separate pdf module).
- Quote to project to milestone billing: QuoteItem.kind (standard/milestone/recurring/pass_through/option; `selected` for options, `position` = entry order). Only standard, milestone and selected option lines count towards the total (quotes/quote-totals.ts on the API mirrors shared-util quoteTotal()); recurring is per month, pass-through at cost. POST /quotes/:id/convert creates the project in one transaction (budget = one-off subtotal pre-tax, retentionPercent copied, one priced Milestone per line of milestoneSchedule(): milestone lines with picked options slotted before the last milestone line, which is final and releasesRetention) and locks the quote's lines and currency (Quote.projectId). Milestones carry amount/billingTrigger/deliverables (Json)/acceptanceCriteria and statuses delivered and accepted (accepted and completed both count as done); entering `accepted` stamps dates and, for a priced on_acceptance milestone, raises a draft invoice via MilestoneBillingService (net of project retention; Invoice.milestoneId unique = one invoice per milestone; POST /milestones/:id/invoice raises one by hand). A failed auto-invoice never undoes the sign-off. Quote scope is structured, not attached: milestone and option lines carry `deliverables` ([{id,label}]) and `acceptanceCriteria` (dropped on other kinds), copied onto the milestone on convert (deliverables as done:false). Quote PDF (PdfGeneratorService.quotePdf, built only via NotificationService.quotePdfBuffer from quote-totals milestonePlan()): page 1 is the priced proposal, the milestone scope follows on its own page(s); the quote-sent mail never lists scope, it only points to the PDF. Quote PDFs default to embedded Inter (SIL OFL TTFs in apps/api/src/assets/fonts/inter, copied to dist/assets by webpack; titles use the InterMedium family, "bold" is SemiBold, spacing tightened for Inter); invoices/receipts still default to Helvetica; a theme font or missing font files fall back to the std-14 fonts. POST /quotes/preview-pdf renders that same PDF from an unsaved CreateQuoteDto (nothing persisted) - apps/client's quote page Preview shows it, so preview = attachment. QuoteAttachment joins a quote to supporting Documents of its client or the client's projects (`attachmentIds` on create/update replaces the list, locked with the lines); the portal shows them with the quote and serves them via GET /portal/quotes/:id/attachments/:documentId/download, gated by viewQuotes (not viewDocuments - attaching is the share).
- Notification: MailerModule hbs templates src/notification/mail/templates (invoice-sent, invoice-paid, invoice-reminder, password-reset-otp, email-verification-otp, login-otp, portal-user-invite, portal-password-reset — the deep-link mails take an optional/derived URL built from APP_URL or PORTAL_APP_URL); handlebars strict — pass every referenced key. Gateway ws namespace /ws/notifications on socket.io path `/api/ws-socket` (under /api so the SPA proxies carry it; apps/client connects via core/realtime/workspace-realtime.service.ts for the live bell and quote refreshes), JWT in handshake auth.token, rooms user:<id>. EventEmitter wildcard enabled; events.gateway is ping-only (never rebroadcast events on it - it's unauthenticated). NotificationGateway rejects portal (`kind`) tokens like JwtAuthGuard.
- pdfmake 0.3: only `const pdfmake = require('pdfmake')` works — exports are this-bound non-enumerable accessors; destructuring or __importStar (import *) break at runtime. setFonts (std-14 Helvetica) then createPdf(def).getBuffer(): Promise<Buffer>.
- Storage: abstract StorageService → local disk (no public route) or S3 by STORAGE_DRIVER/NODE_ENV. Documents: POST /documents is multipart (multer FileInterceptor 'file' + metadata fields in one call); storageKey/size/mimeType derived server-side, name defaults to the file name; emits file.uploaded; document delete also removes the stored file.
- Client portal: ClientPortal (slug globally unique, `@@unique`, auto-generated from client name with `-2`/`-3` retry on collision) 1:1 with Client, has a PortalPermission (viewProjects/viewDocuments/viewQuotes/viewPayments — invoices/payments both gate on viewPayments, there's no separate viewInvoices flag) and many ClientPortalUser/ClientPortalProject. client-portal module: workspace-owner-scoped CRUD for the portal itself (auto-invites the client's own email as first ClientPortalUser on create, auto-shares the client's existing projects); projects.service.ts also auto-creates a ClientPortalProject when a new project is created for a client that already has a portal. portal-users module: workspace-owner-scoped CRUD for ClientPortalUser (invite generates a bcrypt-hashed token in otpSecret as `hash:expiresMs`, 7-day TTL, emits PortalEvents.USER_INVITED).
- Portal permissions: the workspace holds the defaults (`portalViewProjects|Documents|Quotes|Payments`, edited in Settings > Client Portal); a PortalPermission follows them while `inherit` is true and uses its own view* flags once false. Always resolve through common/portal-permissions.ts `effectivePortalPermission()` (PortalContextService, GET /portal-auth/me and the client-portal responses' `effectivePermission` all do) - never read a portal's view* flags directly. PATCH /client-portal/:id takes `inheritPermissions`; sending a view flag alone implies false. PATCH /client-portal/:id/projects/:projectId {active} shares/hides a project. Every client-portal response is the whole portal (permission, effectivePermission, users with project access, project shares).
- Portal user project access: `ClientPortalUser.allProjects` (default true = inherits whatever the portal shares, now and later) or a ClientPortalUserProject list; the list only narrows the portal's active shares (PortalContextService.sharedProjectIds(clientPortalId, portalUserId)). A limited user's billing is narrowed too: PortalBillingService.billingScope()/paymentScope() let them see only project-less invoices/quotes/payments and those of their own projects (lists, details, PDFs, quote attachments, accept/decline), and invoice/quote notifications follow the same rule (recipients(..., { billing: true })). All-projects users still see every client billing record, an unshared project's anonymised. portal-users: POST/PATCH take `allProjects` + `projectIds` (must be the portal client's projects, non-empty when limited), POST /portal-users/:id/resend-invite re-issues the link for an `invited` user, PATCH status suspends/reactivates (an invited user can't be set active), DELETE revokes.
- Portal auth (portal-auth module, unrelated to the above's JwtAuthGuard): separate PortalJwtAuthGuard/@CurrentPortalUser(), payload `{sub,email,clientPortalId,kind:'portal_user'}`; the guard also re-reads the user on every request and 401s unless they still exist, are `active` and belong to that portal, so suspend/revoke take effect immediately — `kind` is the discriminator that keeps the two token types from authenticating each other's routes (the main JwtAuthGuard 401s any token carrying `kind`). POST /portal-auth/{accept-invite,login,forgot-password,reset-password}, GET /portal-auth/me. All four POSTs take the portal `slug` and look the user up within that portal (case-insensitive email) - the same email can be a user of several portals; portal-users stores emails lowercased. Only active users get reset links and a reset never changes status (it can't lift a suspension); login refuses a disabled portal. Reactivating a user suspended before accepting returns them to `invited`; changing a pending invite's email re-sends the invite. accept-invite and reset-password share one private credential-setting method; login checks ClientPortalUserStatus before the password (an invited user's passwordHash is an unguessable placeholder, so checking password first would mislabel it "wrong password"). Mail links embed the portal's slug: `${PORTAL_APP_URL}/:slug/accept-invite|reset-password?token=...&email=...`.
- Portal API (portal-api module, guarded by PortalJwtAuthGuard): GET /portal/{projects,invoices,quotes,payments,documents} (+ /:id, + /invoices|documents/:id/download), each gated by its PortalPermission flag via a shared PortalContextService.require(clientPortalId, flag). Documents: project-less client documents, or documents of a project in the user's sharedProjectIds (a project's document is hidden with its project even when it also carries the clientId). Draft quotes are never visible (404 / not listed). GET /portal/quotes takes `?status=` (sent/accepted/declined/expired) and `?projectId=` (404 unless shared, like the billing lists); quotes carry `projectId`/`project` only when that project is shared with the user (PortalBillingService.visibleProjects), else null. The only writes: POST /portal/quotes/:id/accept {optionIds?} and /decline {reason?} - only for a `sent`, unexpired (through the validUntil day), unconverted quote; accept sets the picked options' `selected`. Both stamp Quote.respondedAt/respondedBy ("Name <email>")/responseNote and emit QuoteEvents.RESPONDED (owner notification quote_accepted/declined + live quote.changed) and CHANGED. A client-accepted quote's lines/currency are locked until the owner moves its status off accepted; moving it back to draft/sent, or re-sending, clears the response. Starting the project stays the owner's call (POST /quotes/:id/convert, no re-accept for an accepted quote). Invoice PDFs reuse NotificationService's existing PDF-building helpers rather than duplicating them.
- Portal billing (portal-api/billing/PortalBillingService): portal invoices carry `project` {id,name}, `total`, `amountPaid`, `balanceDue`; portal payments carry `invoice` {id,number} and `project`. A project is named (and projectId kept) only when it's in the user's sharedProjectIds - otherwise null, never leaking an unshared project. GET /portal/invoices and /portal/payments take `?projectId=` (404 if not visible to the user), plus `?status=` on invoices (never draft) and `?method=` on payments (payments have no status). The portal's quotes/invoices/payments pages share shared/list-filters (one dropdown + a project picker shown only with viewProjects). GET /portal/projects/:id/financials (needs viewProjects + viewPayments): budget (pre-tax), invoiced (sent-or-later, incl. tax), paid, outstanding, overdue, remainingToInvoice (budget minus pre-tax invoiced), retentionHeld (billed milestone invoices until the final one is billed), nextDue; invoices in another currency are counted in otherCurrencyInvoices, not summed. Portal UI reuses shared/invoice-table + shared/payment-table on the Invoices/Payments pages and the project's Invoices/Payments tabs.
- Milestone client review: POST /portal/projects/:id/milestones/:milestoneId/review {decision approve|request_changes, comments[{deliverableId?,body}], criteriaConfirmed} (portal-api/projects/portal-milestone-review.service.ts). Only `delivered` milestones; needs ClientPortalUser.canApproveMilestones (default true, set in the workspace portal-user dialog); request_changes needs >=1 comment, approve needs criteriaConfirmed when criteria exist. Each answer is a MilestoneReview row (round n, unique per milestone - double submits 409), then MilestonesService.update runs as the owner (accepted + acceptedBy "Name <email>" -> usual stamps/invoice/events; changes -> in_progress) and the row is deleted again if that fails. Emits MilestoneEvents.REVIEWED (owner notification milestone_changes_requested; approval relies on the completion notification, worded "Signed off by X"). Deliverables Json may carry note, links[{label,url http(s)}], documentIds (must be documents of the project or, project-less, its client). Portal milestone reads include reviews and amount/billingTrigger/releasesRetention, blanked unless the portal shows payments.
- portal-notifications module: PortalNotification rows are per ClientPortalUser (own read state); REST under PortalJwtAuthGuard at /portal/notifications (list, unread-count, :id/read, read-all). PortalNotificationsGateway is socket.io namespace `/portal` on path `/api/portal-socket` (under /api so the SPAs' /api proxies carry it - dev proxy confs have `ws: true`), admits only active portal-user tokens, one room per user `portal-user:<id>`. PortalNotificationsListener fans domain events out (QuoteEvents.SENT/CHANGED, InvoiceEvents.SENT, DocumentEvents.SHARED, MilestoneEvents.CHANGED) via PortalNotificationsService.recipients(clientId, flag, projectId?) - same rules as portal-api (portal active, effective flag, project actively shared and inside the user's project access). Sockets only signal what changed (milestone.changed / quote.changed / notification.created); pages refetch through the permission-checked REST endpoints. Delivery failures are logged, never thrown back into the workspace action. MilestonesService emits MilestoneEvents.CHANGED on every write and QuotesService QuoteEvents.CHANGED; portal milestone reads `select` deliverables/acceptanceCriteria/deliveredAt/acceptedAt but never billing fields.
- portal-public module (no guard, unauthenticated by design): GET /portal-public/:slug returns minimal branding (client name/company, active) for the client-portal SPA's pre-login screens — nothing sensitive, no ids beyond the slug already in the URL.
- Env: DATABASE_URL, JWT_SECRET, JWT_EXPIRES_IN, REDIS_HOST (default foundrycache; set localhost outside docker), REDIS_PORT, SMTP_HOST/PORT/USER/PASS, SEND_EMAIL_FROM, STORAGE_DRIVER, UPLOADS_DIR, PUBLIC_URL, PORT, APP_URL, PORTAL_APP_URL.

## Client (apps/client/src/app)

- domains/<resource>/: `<resource>.models.ts` (API-shaped interfaces, Decimal→string, ISO date strings), `<resource>-api.service.ts` (HttpClient, base `${API_BASE}/<resource>`), barrel `index.ts`. Resources: auth, workspaces, clients, projects, invoices, quotes, payments, expenses, documents, notifications, reports, client-portals, portal-users (the last two are the workspace-owner-side admin views onto client-portal/portal-users on the API).
- Shared code lives in `@foundry/shared-util` (money/num/isoDay/toApiDate/newId/humanize/invoiceTotal/quoteTotal, CURRENCIES/currencyLabel/searchCurrencies/convertAmount/convertedLabel, Currency/CurrencyRates/ClientStatus/PortalUserStatus/ReconciliationEntry types, API_BASE/toParams/PaginatedResponse/PaginationQuery/apiErrorMessage) and `@foundry/shared-ui` (StatusBadge, PageHeader, EmptyState, Field, fieldError, OptionAutocomplete - the generic HlmAutocomplete single-value picker, and CurrencyAutocomplete built on it) — both also used by client-portal; don't duplicate into either app's own tree, extend the lib instead.
- Dev proxy proxy.conf.json → localhost:3000; docker variant proxy.conf.docker.json → foundryapi:3000.
- Auth: domains/auth/auth.service.ts wraps auth-api.service.ts (login/signup/refresh via /auth/me, user + AES-GCM-encrypted JWT cached via core/storage's SecureStorageService, keys foundry.t/foundry.u); routes /auth/login, /auth/signup, /auth/reset (OTP reset), /auth/verify (email confirmation), /auth/verify-login (sign-in code). signup→/auth/verify, login→/auth/verify-login; the pending email is persisted (domains/auth/pending-verification.ts, keyed verify|login) so the OTP screen survives a mobile tab reload, and ?email deep-links from the mail land straight on it. authGuard/guestGuard read the restored session synchronously (appInitializer runs auth.restore() before the router), so protected routes never flash before redirecting.
- Pages fetch data on init and show skeletons while loading (CSR — no server render). shared/line-items-editor exports LineItemDraft (numeric qty/rate) mapped to/from string API items; shared/entity-sheet is the slide-over create/edit panel most pages build their form around.
- Workspace currency: domains/workspaces/workspace-currency.service.ts (root) holds the rates into the workspace currency. Pages call `fx.refresh()` on init and `fx.ensure(currency)` after saving a record; header totals and charts go through `fx.toWorkspace()`, list rows show the original amount with an `fx.approx()` "≈" subtitle when it isn't already in the workspace currency.
- Client and project pickers (list filters and entity sheets) are `app-option-autocomplete` fed by shared/entity-options.ts (clientOptions/projectOptions, with an optional leading "All clients"/"Not linked" option); pass options as a computed signal, not a getter, or the field's text resets on every change detection.
- Project detail has a Notes tab for the internal Project.notes (saved on its own via PATCH, not part of the edit sheet).
- Portal admin lives on the client sheet's "Portal access" tab (pages/clients/portal-access-panel): on/off, permission source (workspace defaults vs custom), project sharing, and users (invite / manage / resend / suspend / revoke). pages/clients/portal-user-dialog is both the invite and the manage-access dialog ("All shared projects" vs searchable "Specific projects"). Settings > Client Portal holds the workspace default permissions (real); its global on/off switch and Branding section are still mock (settings/portal/portal-settings.store.ts) - no backend.
- Clients page: the New Client sheet's "Portal access" tab is usable before the client is even saved (an "Enable client portal" switch) — on save, if checked, POST /clients then POST /client-portal fire in sequence; a portal-provisioning failure gets its own toast rather than being folded into the client-save error path.

## Client Portal (apps/client-portal/src/app)

Read-only against the real API (no pay-invoice/approve-quote/upload-document/messaging endpoints exist) except portal-auth. Every route lives under `/:slug` (paramsInheritanceStrategy: 'always' so every page and auth screen can read it as a route-bound `slug` input) — the portal runs from its slug on the existing origin rather than a subdomain for now; a dedicated per-tenant domain is a later step.

- domains/auth/: portal-token.store.ts (plain localStorage, not encrypted like the main app's — deliberate scope trim; holds both the JWT and the last-known slug, the latter surviving logout so a bare `/` or a 401 still lands on this portal's own login instead of a dead end), portal-auth.service.ts (`authenticated`/`me`/`slug` signals, restore() called from the app initializer), portal-auth.guard.ts: authGuard (also corrects the URL's slug segment if it doesn't match the signed-in user's real one, preserving the rest of the path), guestGuard, rootRedirectGuard (bare `/` → known slug, else the pages/no-portal landing).
- domains/portal-public/: unauthenticated branding lookup by slug, used by the login/accept-invite pages to show the right client name/initial before anyone has signed in.
- Project budgets/rates render in the client's currency: GET /portal-auth/me carries `clientPortal.client.currency`, exposed as `PortalAuthService.currency()`. Invoices, quotes and payments keep using their own record's currency.
- Nav (layout/portal-shell) is permission-gated from `me().clientPortal.permission`, not a client-side capability guess; the section routes also carry permissionGuard(flag) (re-reads /me) so a hidden section can't be opened by URL. login/acceptInvite complete only after /me has loaded. guestGuard lets another portal's login/invite open while signed in (signing in there replaces the session). No notification bell — no backend for it.
- Messages page is a static "Coming soon" card (icon badge + pill + description in a surface-card), styled like apps/client's settings.html comingSoon pattern — not wired to anything.
- Dropped from the original template concept entirely (fictional, no schema backing): project progress/milestones/deliverables/hours, dashboard activity feed. Project/dashboard views show only real Project fields.

## Conventions

Use domain-driven design. Code is reviewed by codex. Entities/DTOs carry full @ApiProperty metadata; every endpoint documents its response types. Genuinely shared, contract-free code (formatting, generic UI atoms) goes in libs/shared/*; code coupled to a specific API contract (domain models, *-api.service.ts) stays duplicated per app rather than forced into a shared lib that would couple two different backend surfaces.
